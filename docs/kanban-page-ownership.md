# 看板页面归属与通用页面策略设计

## 1. 背景

Docmost 原生看板把一条工作项拆成两部分：

- `database_records` 保存看板字段和排序；
- `pages` 保存工作项正文，并作为看板页面的直接子页面显示在侧边栏。

这种设计保留了“工作项也是文档”的灵活性，但当前页面树和看板关系可以分别修改，导致以下问题：

1. 工作项页面可以通过侧边栏拖拽、移动弹窗、REST 或 MCP 离开所属看板；
2. 页面树无法说明哪些子页面是工作项、哪些只是普通文档，用户容易误操作；
3. 同一页面可以承载多个看板块以及未来的其他面板，任何单一页面类型都会错误地独占页面；
4. 看板接口只校验看板宿主页权限，可能绕过工作项页面自己的查看或编辑限制；
5. 看板移动页面时存在绕过页面树循环检查、跨空间检查、锁和实时通知的路径；
6. `database_records` 没有限制同一页面同时属于多个活动看板；
7. 页面树只展示普通文档图标，用户无法辨认看板宿主页和受看板约束的工作项。

目标是让看板归属成为服务端强制执行的不变量，同时保持 `pages` 为通用文档模型，未来增加日历、审批或其他面板时不需要继续修改页面表结构。

## 2. 明确不采用的方案

不向 `pages` 增加 `pageType`、`nodeType`、`boardId`、`isBoardItem` 或类似业务字段。

原因：

- 一个页面未来可能同时被多个功能引用，单一类型字段会产生冲突；
- 新增面板功能会不断要求扩充枚举并修改页面核心逻辑；
- 业务归属已经存在于对应模块的关系表，重复存储会产生同步和修复成本；
- 页面移动、创建和删除的限制应由可组合策略表达，而不是由页面表承担所有业务状态。

看板身份的唯一事实来源保持为：

- 活动的 `database_blocks` 表示看板宿主页；
- 活动的 `database_records` 表示工作项页面归属。

侧边栏返回的扩展标记和操作能力只是在请求时从关系表计算，不写入 `pages`。

## 3. 业务不变量

原生看板必须满足以下不变量：

1. 一个活动工作项页面最多属于一个活动看板；
2. 工作项页面、看板宿主页和关系记录必须属于同一工作区与同一空间；
3. 工作项页面必须是所属看板宿主页的直接子页面；
4. 通用页面接口不能把工作项移到看板之外，但普通页面可以自由进入、离开看板宿主页；
5. 看板宿主页不独占子树，可以创建普通子页面，也可以同时承载多个看板或其他面板；
6. 看板之间转移工作项只能使用看板专用命令，并在一个数据库事务内完成关系和页面树更新；
7. 前端隐藏或禁用操作只用于改善体验，服务端必须独立执行全部约束；
8. REST、MCP、批量操作和后续内部任务都必须经过相同的页面策略；
9. 读取和修改看板记录时，既要校验看板宿主页权限，也要校验对应工作项页面权限；
10. 失败的事务不能留下孤立页面、重复关系或关系与页面树不一致的中间状态。

## 4. 通用页面操作策略

### 4.1 服务端结构

在页面模块提供 `PageOperationPolicyService`，它只负责注册和聚合实现了统一接口的策略提供方。

策略提供方可以实现以下能力：

- 批量计算页面扩展标记和操作能力；
- 在创建子页面前校验目标父页；
- 在页面重排、换父级或跨空间移动前校验源页面和目标位置；
- 返回稳定的错误代码，供 REST、MCP 和前端统一处理。

数据库模块注册首个提供方 `DatabasePagePolicyContributor`。页面模块不导入数据库模块，也不引用 `database_blocks` 或 `database_records`，从而避免循环依赖和业务硬编码。

后续功能只需注册新的策略提供方。聚合规则采用“限制优先”：任意提供方拒绝操作，页面核心服务就拒绝操作；任何外部请求都不能指定跳过策略。

模块内部创建页面也不能绕过该契约。数据库模块创建工作项页面前，会在同一事务中重新锁定并校验宿主页，然后调用通用 `createChild` 策略；这样同一页面未来叠加审批、日历等扩展时，各模块的限制仍按“限制优先”组合。

### 4.2 通用侧边栏响应

侧边栏节点按请求动态附加通用元数据：

```ts
type PageExtension = {
  provider: string;
  role: string;
  resourceId: string;
};

type PageCapabilities = {
  move?: boolean;
  reparent?: boolean;
  moveToSpace?: boolean;
  createChild?: boolean;
  duplicate?: boolean;
};
```

看板提供方返回：

- 看板宿主页：`provider=database, role=host`，仅禁止跨空间移动和复制；同空间排序、换父级及普通子页面仍可使用；
- 工作项页面：`provider=database, role=record`，禁止换父级、跨空间移动和复制，但允许在所属看板内排序。

同一页面存在多个扩展关系时，元数据保留全部 `extensions`，能力使用“限制优先”合并。这样未来面板只注册自己的关系和策略，不需要改 `pages`，也不会覆盖看板关系。

这些字段不是页面属性，不持久化，不参与文档导出，也不改变公开页面数据模型。

### 4.3 前端结构

页面树只理解通用 `extensions` 和 `capabilities`：

- `capabilities.move === false` 时不注册拖拽源；
- `capabilities.reparent === false` 时仍可在同一父页内排序，但不能改变父页；
- `capabilities.moveToSpace === false` 时不显示移动空间入口；
- `capabilities.createChild === false` 时不显示新增子页面入口；
- `capabilities.duplicate === false` 时不显示复制入口；
- 扩展标记由可注册的渲染器展示，看板模块提供看板和工作项图标及提示。

即使旧客户端没有这些能力字段，服务端策略仍会拒绝非法操作。

## 5. 看板专用操作

### 5.1 创建工作项

创建页面和插入 `database_records` 必须在同一事务中执行。页面直接创建到看板宿主页下，字段写入前按 schema 校验。

### 5.2 移入看板

只允许通过 `records/attach-page`：

1. 校验目标看板编辑权限；
2. 校验源页面编辑权限以及完整工作区边界；
3. 拒绝看板宿主页本身、目标看板祖先及会造成循环的页面；
4. 在事务中锁定相关空间页面树；
5. 创建目标关系并通过统一页面服务移动；
6. 提交后发送页面树实时事件和看板查询失效事件。

### 5.3 看板间转移

允许“移动到另一个看板”，但不允许先解除归属再成为普通页面。源关系失效、目标关系建立和页面移动必须在一个事务内完成，对事务外始终表现为有且只有一个归属。

服务端在事务内读取源工作项的最新字段，只迁移目标 schema 中名称和类型兼容、且值仍满足目标选项约束的字段。客户端不能用打开页面时的整份旧快照覆盖源记录；移动请求只允许显式指定目标看板的分组字段。目标分组没有同名选项时，客户端选择目标看板的第一个有效选项。这样不同 schema 的看板可以安全转移，且并发更新的优先级、人员等共同字段不会被旧页面覆盖。

### 5.4 移出看板

严格归属模式下取消“移出看板/仅移除工作项”操作。用户可以：

- 移动到另一个看板；
- 将工作项及其页面移入回收站；
- 在恢复页面时恢复原看板关系。

### 5.5 删除看板

当前实现没有独立的可复用“数据源”实体。编辑器中的 `databaseBlock` 与 `database_blocks` 一一对应，schema、视图和提供方配置保存在同一条记录中；`database_records` 保存工作项关系，工作项正文保存在 `pages`。

因此删除编辑器节点不能只改变富文本。统一删除流程为：

1. 前端菜单或节点选择删除先打开确认框，取消时不发送内容事务；
2. `POST /databases/delete` 必须同时提交 `databaseId + pageId + blockId`，服务端核对精确所有权，并重新校验宿主页和每个活动工作项页面的编辑权限；
3. 事务中锁定看板及记录，把工作项页面子树移入回收站，并归档被删除看板及其记录；
4. 事务提交后再发送页面树、看板查询失效事件和 `database.deleted` 审计；
5. 最后发送带确认标记且不进入撤销历史的编辑器事务删除 `databaseBlock` 节点。

删除接口保留已删除记录作为幂等凭据。客户端在“服务端已提交但响应丢失”后使用相同页面和块上下文重试，会得到 `alreadyDeleted=true`，不会再次回收页面、重复审计或重复广播。活动原生工作项存在错误父级、跨空间或跨工作区关系时，删除失败并要求先修复关系，不会静默丢弃关系后留下来源不明的普通页面。

复制到其他页面的块、伪造 `blockId` 的块以及同一页面上的重复引用都不能直接删除来源看板。无效块只移除当前节点；完全相同的重复引用也先逐个移除，只有最后一个有效所有者引用才能执行看板删除。客户端删除守卫按 `databaseId + blockId + 节点位置` 路由确认请求，服务端内容钩子按 `databaseId + blockId` 判定所有者消失。

MCP/REST 的页面 `replace` 在修改 Yjs 文档前执行相同的模块化生命周期预检。Markdown 或 HTML 往返丢失 `databaseBlock` 时返回 `DATABASE_EXPLICIT_DELETE_REQUIRED`，不会把格式损失解释为确认删除；调用方必须先使用专用删除命令。持久化阶段保留第二次校验，且直接调用会传播真实错误，不再返回假成功。

外部 APITable 看板删除只归档 Docmost 中的块和本地关系，不删除远端数据表或记录；确认框和审计元数据都会明确 `externalDataPreserved=true`。

工作项页面内的嵌套看板不会被永久归档。它们随页面子树进入回收站，恢复页面时仍可恢复原有嵌套看板；只有用户明确删除的看板解除关系。工作项页面恢复后不再属于已经删除的外层看板，可作为普通页面继续使用。

协同保存的内容生命周期钩子还会核对 `database_blocks.page_id`。复制到其他页面的伪造或残留块不具备数据源所有权，删除该副本不会归档原宿主页上的看板。

### 5.6 并发与锁顺序

关键写路径统一遵守“空间树锁 -> 页面锁 -> 看板锁 -> 工作项关系锁”的顺序：

- 创建普通子页面时，在同一事务内锁定并重新校验父页，再执行扩展策略、位置计算和插入；
- 创建工作项时先锁宿主页，再锁看板，避免与协同保存删除形成反向等待；
- 看板间移动先按稳定顺序锁定涉及的空间与页面，重新校验页面和宿主页权限，再锁看板与关系；
- 删除看板先锁宿主页和看板，再锁记录与工作项页面；
- 从回收站恢复页面时先锁父页，再锁待恢复页面。

同一块并发创建时，宿主页行锁负责串行化，事务内再次查找已有看板并返回获胜记录。服务端不会产生两条本地看板记录；外部提供方请求已发出但本地事务失败时的远端补偿仍由 KAN-703 跟踪。

字段、视图和工作项更新也在看板行锁内重新读取当前 schema。列选项重命名或删除使用专用事务命令，同时迁移活动记录、回收站中可恢复记录和旧版 `metadata.records`；通用字段更新接口只允许新增或重排选项，不能绕过专用命令删除旧选项。并发列操作中只有一个请求获胜，失败方收到稳定冲突并重新加载；相同请求在响应丢失后的重试按当前 schema 幂等返回。

## 6. 权限与安全

1. 列表接口先校验看板宿主页，再批量过滤用户无权查看的工作项页面；
2. 更新、排序、转移和回收工作项时必须校验对应页面编辑权限；
3. 状态、单选、多选和值类型按字段 schema 校验，重复/空选项、文本字段伪造选项和未支持字段类型均由服务端拒绝；人员字段只能引用当前工作区内未删除、未停用的用户；
4. 所有数据库查询限定 `workspaceId`，不能仅凭 UUID 访问跨工作区对象；
5. 唯一部分索引防止并发请求为同一页面创建多个活动归属；
6. 页面树变更使用事务级锁、循环检查和同空间检查；
7. 客户端提交的扩展标记、能力或策略上下文一律不可信且不接收；
8. 错误响应不泄露目标看板或无权页面是否存在。

## 7. 一致性、实时同步与审计

### 7.1 数据一致性

- 为活动记录增加页面归属唯一索引；
- 迁移先识别重复归属、跨空间关系和错误父级，按确定性规则保留一条并修复页面位置；
- 看板创建、工作项创建、字段更新与页面标题同步使用事务；
- 字段和记录写入基于事务内锁定后的最新值合并，页面标题同步只更新主标题 JSON 路径，不覆盖并发修改的其他字段；
- 列选项迁移同时覆盖关系表记录、回收站记录和旧版元数据记录；字段改名同步更新引用它的视图 `groupBy`；
- 字段类型转换在没有显式转换器前失败关闭，外部 APITable schema 只能在来源提供方修改；
- 禁止读取接口隐式创建缺失页面，修复动作改为显式维护任务。

### 7.2 实时同步

- 页面位置和标题变化复用 `WsTreeService`；
- 页面更新事件使用数据库实际返回的页面 ID 与工作区 ID，不依赖调用方重复传入工作区字段；
- 看板记录、字段、视图和排序变化发送数据库资源事件；
- 客户端收到事件后按 `databaseId` 精确失效查询；
- 本轮新增的看板写入与恢复事件在事务提交成功后发送；仓库其他通用页面事件仍需逐步迁移到统一提交后事件源。
- 数据库事务提交后的审计、页面树事件和查询失效均按 best-effort 执行，发布失败记录服务端错误但不把已经提交的创建、移动或列变更伪装成回滚；可靠补发仍由事务 outbox 任务跟踪。
- 编辑器注册 `DatabaseBlockDeleteGuard`，本地删除看板节点必须先完成服务端删除；服务端协作持久化增加可注册的 `PageContentLifecycleService`，主服务进程可识别旧客户端或内容替换操作移除的数据库块，并在保存内容的同一事务中执行数据库模块策略。
- 直接页面更新先做生命周期预检，再进入 Yjs；保存异常会向 REST/MCP 传播，连接清理失败不会覆盖原始业务错误。

### 7.3 审计

新增看板资源审计事件：创建/删除看板、修改 schema、创建/更新/排序/转移/回收工作项。恢复继续使用通用 `page.restored` 事件。删除事件记录看板、工作项和回收页面数量；列选项操作记录重命名/删除、前后选项及受影响记录数量；其他审计记录包含工作区、空间、看板 ID、工作项页面 ID、操作类型和必要的前后状态摘要，不记录完整正文或完整字段值。

## 8. 导出、公开访问与 MCP

- Markdown/HTML 导出需要通过权限感知的投影服务展开看板摘要，不能静默丢失数据库块；
- JSON 保持编辑器结构，并可附加显式请求的看板投影，不把运行时侧边栏能力写入文档；
- 公开分享只返回分享范围内可见的工作项，受密码或能力令牌保护的页面继续执行原校验；
- MCP 获取页面复用相同投影和页面权限；
- MCP 页面移动工具复用 `PageService`，因此不能绕过看板归属；
- MCP/REST 使用 Markdown、HTML 或 JSON 替换含看板的页面时必须保留看板块，否则收到冲突并保持原内容；
- 未来如增加看板 MCP 工具，应使用专用 schema、作用域和审计事件，不复用任意页面移动参数模拟看板操作。

## 9. 性能与兼容性

- 侧边栏扩展信息必须批量查询，禁止逐页面查询；
- 工作项列表已使用批量页面和权限检查；游标分页保留为下一阶段任务；
- 旧客户端仍可读取基础侧边栏字段，但非法写操作会收到明确冲突错误；
- 当前客户端将不可逆看板删除排除在编辑器撤销历史之外；旧客户端恢复出的已归档块仍可通过幂等删除流程安全清理；
- APITable 提供方必须声明功能能力，不支持真实 Docmost 子页面时拒绝页面附加和转移；
- 外部 APITable 的字段创建、改名和列结构操作在 Docmost 中隐藏并由服务端拒绝，避免只改本地镜像而未修改远端 schema；
- 不改变 `pages` 表，降低与上游 Docmost 页面模型合并时的冲突；
- 所有新增响应字段均为可选，保持现有客户端类型兼容。

## 10. 用户可见变化

1. 侧边栏中的看板页显示看板标记，工作项页显示受看板管理的标记；
2. 工作项页可以在所属看板的子节点之间排序，但不能拖到其他父页，也不再显示“移动到空间”或复制；
3. 看板宿主页仍可创建和接收普通子页面；这些普通页面不会自动变成工作项；
4. 看板内保留“移动到另一个看板”和“移入回收站”，取消“移出看板”；
5. 非法移动由服务端拒绝，并显示可理解的错误提示；
6. 同一页面可以放置多个看板或未来其他面板，普通文档的创建、拖拽、移动和公开访问保持不变。
7. “New task” 使用较小的次要操作字号，输入任务名称后点击其他位置即可创建，不再强制按 Enter。
8. 看板右上角更多菜单增加“删除看板”；全选看板后按 Delete/Backspace 也会打开相同确认框，确认后工作项页面进入回收站。
9. 中文输入法候选确认不会误创建任务；创建失败时草稿标题保留，可直接重试，也不会由 Enter 与失焦产生重复请求。
10. 复制或重复的看板块显示“移除看板块”，不会误删来源看板；外部 APITable 删除确认会说明远端数据仍被保留。
11. 列重命名会原子更新现有和可恢复工作项；只允许删除真正没有活动卡片的列，筛选隐藏卡片时不会误显示为“空分组”。
12. 看板按当前视图的 `groupBy` 字段分组，分组字段改名后视图、卡片拖拽、表格和侧栏编辑仍保持一致且不能清空该字段。

## 11. 参考行为

Notion 的官方 API 把数据源行建模为页面，把 schema 和视图作为独立对象。本项目只参考这个模型原则，不复制其接口或存储结构。参考：

- <https://developers.notion.com/reference/page-property-values>
- <https://developers.notion.com/guides/data-apis/working-with-databases>
- <https://developers.notion.com/reference/view>

本项目不会照搬 Notion 的实现；这里只采用“条目是页面、业务关系由模块维护、视图配置独立”的模型原则。

### H. 系统诊断与触发标记

系统状态页增加 owner 专属的“系统诊断”区块，当前状态按工作区隔离，接口继续由 JWT、REST 读取 scope 和服务端 owner 角色三层校验保护。前端只接收计数、阈值和状态，不接收页面正文、文档 ID、外部数据源凭据或异常堆栈。

当前检查项如下：

1. `external_apitable_active`：存在外部 APITable 数据源时标记为信息，不直接判定为故障，用于触发 KAN-703 的评估。
2. `large_board`：有效工作项达到 500 的看板被标记为需要关注，同时显示最大工作项数量，用于判断是否触发 KAN-706。
3. `orphan_database_source`：看板创建超过一小时后，宿主页不存在、已删除、工作区或空间不一致，或者正文中不存在完全匹配的 `databaseId + blockId` 节点时标记；用于 KAN-712，不自动删除。
4. `invalid_database_relation`：有效工作项与看板、工作项页面的工作区、空间或父子关系不一致时标记为错误，用于判断是否需要 KAN-713 修复命令。
5. `realtime_invalidation_failure`：服务端实际发布看板缓存失效通知失败时记录，当前状态显示最近 24 小时的采样记录，用于判断是否需要 KAN-716。

状态请求最多每分钟重新计算一次，后台每 15 分钟主动扫描所有有效工作区。前四项只在“首次发现”和“恢复正常”时复用现有审计表写入记录；实时投递失败按工作区和诊断代码在单进程内五分钟采样一次，避免持续故障刷爆审计。历史记录遵循工作区现有审计保留周期，不增加迁移、数据表、轮询队列或自动修复行为。
